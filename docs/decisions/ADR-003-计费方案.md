# ADR-003: 计费方案

## Status

Accepted (2026-08-19) — MVP Stripe 路径已锁定；国内支付选型收口方案经用户 2026-08-26 拍板通过（Phase 1 = Stripe card+alipay+wechat_pay 年付优先，Phase 2 = 微信 Native + 支付宝电脑网站支付直连经 PaymentProvider 切换，第四方聚合 d1 明确否决）。决策人：用户（产品负责人）。拍板方式：逐项评审后整体同意（含所有待确认子项）。

> 变更记录：2026-08-26 由商业化决策分析师收口原 OPEN 子项"国内支付选型"，新增方案对比矩阵、推荐路线与 `PaymentProvider` 接口草案。定价档位配套调整见 `docs/market/pricing-strategy.md`（两档制：Free / Pro ¥59）。同日经用户拍板通过（逐项评审后整体同意，含所有待确认子项），本文决策全部生效。

## Background

计费为 P1 功能（Spec 第 2 节），需满足：席位计费雏形（Stripe Checkout + Portal + webhook）、成员数变更同步 subscription quantity（AC-08）、扣款失败触发催缴不立即中断服务（AC-09）。目标市场为中国大陆（Spec 第 1、10 节）。候选：

- **A. 仅 Stripe（跨境）**：Checkout/Portal/webhook 成熟，集成快；但 Stripe 在中国大陆需跨境收单，存在合规与外汇结算不确定性，国内持卡/扫码体验不如本地钱包。
- **B. 仅微信支付 / 支付宝**：国内直连体验与合规最稳，但订阅（按席位按月续费 + 数量变更）需自行实现账单与催缴，工作量高于 Stripe 订阅。
- **C. Stripe 跑通 MVP 订阅逻辑 + 抽象 `PaymentProvider` 接口，生产环境可切换微信/支付宝**：兼顾速度与可替换性。

## Decision（MVP 阶段，2026-08-19 已锁定并实现）

MVP 采用 **Stripe 作为默认计费实现**（方案 A 的集成方式 + 方案 C 的抽象）：

- 升级：POST `/api/v1/workspaces/:wid/billing/checkout`（Owner 专属）创建 Stripe Checkout Session，`quantity` = 当前 workspace 活跃席位数。
- 自助管理：Stripe Customer Portal 处理升降级/付款方式（不另建账单 UI）。
- 回写：POST `/api/v1/billing/webhook` 用 `Stripe-Signature` 验签后处理 `checkout.session.completed`、`customer.subscription.updated`（同步 `subscriptions.quantity`，AC-08）、`invoice.payment_failed`（置 `past_due` 并触发催缴，AC-09，不立即中断服务）。
- `subscriptions` 表存 `stripe_customer_id` / `stripe_subscription_id` / `quantity` / `status`（schema 见 `db/schema.sql`）。
- 抽象：计费逻辑经 `PaymentProvider` 接口封装（createCheckout / syncSubscription / handleWebhook），使支付通道可替换，不为 Stripe 硬编码业务规则。

## Consequences（MVP 阶段）

正面：

- 用最少的集成成本跑通完整订阅生命周期（含席位数量同步与催缴），满足 P1 验收。
- webhook 的 quantity 同步天然覆盖 AC-08，payment_failed 状态机覆盖 AC-09。
- 席位拦截已在邀请链路生效，免费层→付费的转化触发器真实存在（非纸面设计）。

负面 / 代价：

- Stripe 跨境在中国大陆的合规/结算风险未消除（本 ADR 第 3、4 节收口）。
- 抽象层尚未落地（见上表），接国内通道前必须先完成重构，否则"可切换"只是文档承诺。

## 国内支付选型收口（2026-08-26 已拍板通过）

> ✅ 2026-08-26 用户拍板：推荐路线与 PaymentProvider 接口草案均获批准。

### 1. 决策输入

- 目标用户：5–30 人中小团队的创始人 / PM 画像（Spec §1），付费决策链短，习惯支付宝/微信扫码，**外币信用卡持卡率低**。
- 产品形态：席位订阅制（月付/年付），单席价格 ¥59/人/月（定价确认见 `docs/market/pricing-strategy.md`）。
- 部署：腾讯云 CloudBase + 国内 CDN（Spec §4），满足 ICP 备案的服务器境内要求，但**备案主体资质是否齐备未确认**——这是 Phase 2 直连方案的先决条件。
- 工程现状：Stripe 全链路已实现（见上表），roadmap M3 为"国内支付接入"预估 2 周、"正式定价上线+付费页面"0.5 周（`docs/market/product-roadmap.md`）。
- 关键技术事实（影响所有通道的订阅形态）：**微信支付的"委托代扣"、支付宝的"周期扣款"权限对普通 SaaS 类目审核极严；Stripe 的 Alipay / WeChat Pay 付款方式属单次授权（single-use），不支持自动续扣**。因此无论选哪条通道，中国大陆用户的订阅续费现实形态都是"一次性付款 + 到期提醒引导重新付款"，仅外币卡走 Stripe card 可自动续扣。AC-09 的催缴语义在国内通道下从"webhook 自动重试"调整为"到期前邮件提醒 + 一键续付链接"。

### 3. 明确否决项

**d1（虎皮椒/PayJS/蓝兔等个人友好第四方）否决**。理由：SaaS 订阅是持续性经营业务，二清合规红线、资金安全与发票闭环是硬伤；一旦通道关停，存量客户续费全部中断，损害品牌信任。该类方案仅适合个人开发者一次性变现，不进入路线图任何阶段。

### 4. 推荐路线（Phase 1 → Phase 2）

表：分阶段支付通道推荐表

| 阶段 | 主通道 | 说明与前置条件 |
|------|--------|----------------|
| Phase 1（现在 → Beta/GA 初期） | **Stripe Checkout（card + alipay + wechat_pay）**，境外主体（香港优先） | 复用已实现的 Checkout/Webhook 全链路，改动集中在 checkout 参数与环境配置；国内客户以支付宝/微信扫码完成首购，**年付优先推荐**（一年一次续费摩擦最小，规避 single-use 无法自动续扣的限制）；外币卡客户保留自动续扣。前置条件仅为境外实体与银行账户；若实体暂未就绪，继续 test mode + 种子期免费策略（competitive-analysis §6"前 100 团队 6 个月免费 Pro"），不阻塞 Beta |
| Phase 2（GA 后、资质齐备） | **微信支付 Native 直连 + 支付宝电脑网站支付直连**双通道，经 `PaymentProvider` 切换；Stripe 降级为海外客户备选 | 前置条件：企业营业执照 + 对公账户 + ICP 备案域名（CloudBase 境内部署已满足服务器侧要求）。费率 0.6% 对比 Stripe 跨境约省 60%–80% 手续费，T+1 人民币到公户消除结汇环节。双通道并行而非二选一：覆盖两类钱包用户，互为容灾 |

选择理由（对应 Spec §10"必要时替换为国内支付"）：

1. **Phase 1 不引入新集成面**。M3 时间盒只有 2 周（roadmap M3），若直接上直连，需同时完成 PaymentProvider 重构 + 双通道对接 + 备案等待，时间盒必然爆。Phase 1 用最小改动让国内客户真实付得了钱，把"验证付费意愿"提前。
2. **Phase 2 选直连而非持牌聚合**：费率相当（0.6% vs 0.5%–0.8%），但直连文档质量、SDK 稳定性、退款 API 与官方风控沟通效率均优于中间层；避免多一层清结算依赖。若团队人力不足，d2 持牌聚合可作为 Phase 2 的降级备选（接入工时相近，代价是 SLA 与对账复杂度）。
3. **年付优先的产品化处理**：Phase 1 起定价页将年付设为默认选中态（见 `docs/market/pricing-page-spec.md`），既是转化策略，也是对"国内通道无自动续扣"这一约束的结构性缓解。

### 5. PaymentProvider 抽象接口设计草案（对接现有 billing 代码）

目标：将现有 Stripe 专属逻辑收敛到接口之后，使 Phase 2 双直连通道可在不改业务层的前提下接入。以下为 TypeScript 接口签名草案（放置于 `web/lib/payments/types.ts`，命名沿用项目 camelCase/PascalCase 约定）：

```ts
/** 支付通道标识 */
export type ProviderId = "stripe" | "wechatpay-native" | "alipay-page";

export type BillingPeriod = "monthly" | "yearly";
export type SubscriptionStatus =
  | "active" | "trialing" | "past_due" | "canceled" | "incomplete";

export interface CheckoutRequest {
  workspaceId: string;
  seats: number;                 // 购买席位数（= workspace.seatLimit，审计 F-11 口径）
  period: BillingPeriod;         // 年付优先（Phase 1 转化与续费摩擦策略）
  successUrl: string;            // 必须先过 safeRedirectUrl 同源校验（复用 checkout/route.ts 现有函数）
  cancelUrl: string;
}

export interface CheckoutResult {
  /** 跳转型通道（Stripe Checkout / 支付宝电脑网站支付）：前端 window.location.href 跳转 */
  redirectUrl?: string;
  /** 扫码型通道（微信 Native）：返回 code_url，前端渲染二维码并轮询订单状态 */
  qrCodeUrl?: string;
  /** 通道侧订单号（Stripe session.id / 微信 prepay_id / 支付宝 trade_no），幂等与对账用 */
  providerOrderId: string;
  providerId: ProviderId;
}

export interface PaymentPortalResult {
  url: string;                   // 自助管理入口（发票/换绑/取消）
}

/**
 * 统一支付通道接口。
 * 契约：实现不得抛出未分类异常——验签失败抛 PaymentWebhookError，
 * 其余失败以 Result 形式返回，保证 webhook 路由可统一应答。
 */
export interface PaymentProvider {
  readonly id: ProviderId;
  /** 是否原生支持自动续扣（决定到期策略：true=通道自动重试；false=到期邮件提醒+一键续付链接） */
  readonly supportsAutoRenewal: boolean;

  createCheckout(req: CheckoutRequest): Promise<CheckoutResult>;

  /** 自助管理入口；通道不支持时返回 null，前端据此隐藏按钮（对齐 status 路由 stripeReady 先例） */
  createPortal(ctx: { workspaceId: string }): Promise<PaymentPortalResult | null>;

  /**
   * 验签并解析回调为统一事件。rawBody 必须为原始文本（对齐 Stripe webhook
   * `await req.text()` 取原始体的既有约定，见 ADR-005）。
   */
  parseWebhook(rawBody: string, headers: Record<string, string>): UnifiedBillingEvent;
}

export type UnifiedBillingEvent =
  | { type: "checkout.completed"; workspaceId: string;
      providerCustomerId: string; providerOrderId: string;
      seats: number; period: BillingPeriod }
  | { type: "subscription.synced"; providerOrderId: string;
      status: SubscriptionStatus; quantity: number; currentPeriodEnd?: Date }
  | { type: "payment.failed"; providerOrderId: string }        // → past_due（AC-09 语义）
  | { type: "subscription.canceled"; providerOrderId: string }; // → plan=free + seatLimit 回落（A-7/F-11 语义）

/** 注册表 + 工厂：路由层只依赖接口，不 import 具体 SDK */
export function getPaymentProvider(id?: ProviderId): PaymentProvider;
```

落地要点（Phase 2 启动时的改造清单，预估含在上文 2 周 M3 工时内）：

1. **包一层，不改行为**：将 `checkout/route.ts`、`billing/webhook/route.ts` 内的 Stripe 调用平移进 `StripeProvider`，事件映射到 `UnifiedBillingEvent`；三端点对外契约（路径/鉴权/响应信封）不变，SPEC §5 端点清单无需变更。
2. **数据模型增量**：`subscriptions` 增加 `provider VARCHAR` 与 `provider_order_id VARCHAR` 两列（nullable 起步，down migration 删列即可，符合 Spec §10 可回滚约束）；存量 Stripe 数据回填 `'stripe'`。幂等表 `processedStripeEvent` 泛化为 `processed_payment_event(provider, event_id)`。
3. **Webhook 路由分发**：每通道独立子路径（如 `/api/v1/billing/webhook/wechat`、`/alipay`），各自验签后进入统一事件总线；不共用单一路由做 header 嗅探，降低串扰风险。
4. **续费编排**：`supportsAutoRenewal = false` 的通道由定时任务扫描 `currentPeriodEnd` 临期（建议 T-7/T-1 两轮）发送续付邮件；该任务同时服务于 Stripe 外币卡客户的到期提醒兜底。
5. **对账兜底**：双直连通道增加日终对账拉取（微信/支付宝均有账单下载 API），弥补扫码场景用户关闭页面前回调丢失的长尾。

### 6. 决策状态

- MVP Stripe 路径：维持 **Accepted**（已实现并通过验收映射 AC-08/09）。
- 国内支付最终选型：**DECIDED（2026-08-26 用户拍板通过；决策人：用户，产品负责人）**。执行第 4 节推荐路线（Phase 1 = Stripe card+alipay+wechat_pay，年付优先；Phase 2 = 微信/支付宝直连双通道经 `PaymentProvider` 切换）；第四方聚合 d1 明确否决，不进入任何阶段。若未来需要调整组合（例如跳过 Phase 1 直接直连，或采用 d2 持牌聚合），仅需替换第 4 节阶段表，接口草案与改造清单不受影响。
- 定价两档制（Free / Pro ¥59，年付 ¥590/人/年）已于 2026-08-26 随 `docs/market/pricing-strategy.md` 一并拍板生效；`STRIPE_PRICE_ID` 与通道费率配置自即日起冻结（呼应本 ADR 原 OPEN 项第 4 条），调整需重新评审。
