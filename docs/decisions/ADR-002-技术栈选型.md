# ADR-002: 技术栈选型

## Status

Accepted (2026-08-19) — 锁定，版本已锚定（见 Spec 第 4 节）。

## Background

MVP 目标是用最小团队、最快速度跑通一个对外多租户协作 SaaS，同时满足 P0 红线（RLS 引擎层隔离、argon2id、JWT 15min/refresh 7d）。选型需权衡：学习成本、生态成熟度、部署成本、可回滚性，以及团队熟悉度。候选路径：

- **A. 纯前端 + BaaS（如 CloudBase 文档数据库）**：上手快，但文档数据库无 RLS 行级安全，难以满足引擎层隔离红线，且 argon2id/JWT 控制弱。
- **B. 前后端分离（React SPA + NestJS + PostgreSQL）**：隔离与类型共享好，但 MVP 需维护两个部署目标，起步慢。
- **C. Next.js 全栈（App Router Route Handlers + Prisma + PostgreSQL）+ 成长时抽 NestJS**：单语言贯通前后端，单部署目标最快跑通，RLS 在 PG 引擎层满足红线，Prisma 迁移可逆契合"可回滚"约束。

## Decision

采用方案 **C**，版本锚定如下（来自 Spec 第 4 节，锁定不可随意升级）：

- 前端：Next.js 16.2.6（App Router）+ React 19.2；Tailwind CSS 4 + Radix UI。
- 图标：Lucide（`lucide-react`）钉确切版本（禁 emoji、禁混用，与 Spec 第 8 节及 P0 规则一致）。
- 后端起步：Next.js Route Handlers（全栈一体）；多端/AI 出现时抽独立 API 层 NestJS 11（Fastify），复用 TS DTO + Prisma 模型。
- ORM：Prisma 6（≥6.15.0），迁移可逆（down migration）契合可回滚约束，类型与前端共享。
- 数据库：PostgreSQL 18.4（RLS 行级安全成熟，多租户隔离引擎层强制）。
- 认证：Better Auth（TS 原生，sessions/MFA/orgs 插件，Prisma 适配器）；密码 `argon2id`。
- 令牌：access JWT 15min + refresh 不透明串 7d 轮换（refresh 存 `sessions.refresh_hash`，详见 ADR-001 / schema.sql）。
- 计费：Stripe（Checkout / Portal / webhook），见 ADR-003。
- 部署：腾讯云 CloudBase + 国内 CDN（目标市场中国大陆）。

前端依赖必须显式包含 `lucide-react` 钉版本，架构侧不重选图标库（Spec 已锁 Lucide 一套 SVG）。

## Consequences

正面：

- 单语言（TypeScript）贯通前后端，类型从 Prisma schema 生成后在 Route Handler 与 React 间共享，减少契约漂移。
- 单部署目标（Next.js on CloudBase）最快跑通 MVP，省去独立后端运维。
- PostgreSQL 18.4 + RLS 满足数据隔离红线；Prisma 迁移 `down` 满足可回滚约束。
- Better Auth 原生支持多租户 orgs 插件与 session/refresh 机制，减少自研认证面。

负面 / 代价：

- Prisma 在 Serverless 下有冷启动重（查询引擎开销），Spec 第 11 节已登记为已知坑，备选 Drizzle，MVP 影响可控。
- 全栈 Route Handlers 起步快，但业务逻辑膨胀后须及时抽 NestJS，避免 Handler 里堆业务（已在"后端生长"路径中规划）。
- Better Auth 的 session 表与本项目 `sessions`（refresh_hash）职责需对齐：access 走 JWT 插件（无状态），refresh 走本项目 `sessions` 表（有状态、 argon2id 哈希），避免两套 refresh 机制并存。
- 锁定版本意味着后续升级需走变更流程，不能随意 `latest`。

## Related ADRs

- ADR-001（多租户隔离方案）：技术栈的 PostgreSQL 18.4 + Next.js Route Handler 是 RLS 注入点（`SET LOCAL app.workspace_id`）的承载层。
- ADR-003（计费方案）：Stripe 接入在 Next.js Route Handlers 内实现，依赖本技术栈的 Webhook 验签能力。
