### 为什么这个区别对将后有实质影响

| 原论断 | 修订后论断 | 对"将来能否收编"的含义 |
|---|---|---|
| 有 P0 漏洞，收编前必须**重写**鉴权 | 鉴权已实现但**零执行零测试** | 前者：收编门槛是重写 + 安全审计；后者：收编门槛是补执行路径 + 测试覆盖 |

两者都是"暂不收编"的充分理由，但**成本量级不同**。原论断会让人高估收编难度、并在将来错误地把"已写好的鉴权"当成待建项重做一遍。

**需同时说明的边界**：该鉴权代码从未运行过（`ws` 依赖缺失、无 compose 服务、无任何测试），因此"零执行零测试"不等于"已验证可用"。修订后的正确定位是**未验证**，而非**已验证**或**有漏洞**。

## 2. 新决策：协同孤儿彻底摘除

用户已批准把协同相关孤儿**彻底摘除**，而非继续"保留但断开"。

### 2.1 摘除范围

| 对象 | 内容 |
|---|---|
| 服务端目录 | `server/collab/` 整个目录（`persistence.ts`、`y-websocket-server.ts`、`ARCHIVE-NOTE.md`） |
| 前端组件 | 3 个零挂载组件：`CollaborationProvider.tsx`、`CollaborationCursor.tsx`、`PresenceIndicator.tsx` |
| 纯协同依赖 | 5 个：`yjs`、`y-websocket`、`y-indexeddb`、`lib0`、`y-prosemirror` |

### 2.2 依据

**这是成熟度评分里少数能真实提分的动作**，按 `references/01-standards/production-readiness-scorecard.md` 七维逐条判定：

| 维度 | 影响 | 证据 |
|---|---|---|
| 测试 + 回归 | **正向** | `scripts/zero-coverage-baseline.txt:305,306,320,323` 四行（CollaborationCursor / CollaborationProvider / OnlinePresence / PresenceIndicator）离开分母；该门禁是 shrink-only，删除即真实收缩 |
| 安全 | **正向** | 依赖树减少 5 个包，`pnpm audit --prod --audit-level=high` 的审计面同步缩小 |
| 契约 / 无障碍 / 性能 / 可观测 | 中性 | 这些能力从未对外提供，摘除不改变任何已交付契约 |
| 发布安全 | 中性 | 不涉及发布链路 |

对照另两个选项：**维持现状** = 0 变化（不降分也不提分）；**收编进主干** = 短期**净降分**（新增从未审计的 WS 鉴权面、无测试新代码进主干、新增常驻服务需监控/备份/日志轮转），且 `@tiptap/extension-collaboration` 与 StarterKit 的 `undoRedo` 互斥，收编 = 换编辑器历史管理架构，成本高于"补个 package.json"。

### 2.3 前置核实（摘除前已确认无消费者）

| 依赖 | 唯一消费者 | 是否可摘 |
|---|---|---|
| `y-prosemirror` | `web/components/CollaborationCursor.tsx`（type-only import） | 是 |
| `y-indexeddb` | `web/components/CollaborationProvider.tsx` | 是 |
| `yjs` / `y-websocket` / `lib0` | 协同链路 | 是 |

### 2.4 明确不做

- **不删 `yjs_persistence` 表与迁移** `20260912000004_add_yjs_persistence`：删表需写 down 迁移，收益为零、风险为正，schema 保持不变
- **不改 `web/prisma/schema.prisma`** 中 `YjsPersistence` model：同上
- **不碰 `web/**`、`package.json`、`lockfile`**：由并行 worker 执行，本文只记录决策

## 3. 后果

**正面**

- 零覆盖基线收缩 4 行，是成熟度评分中可量化的真实提分
- 依赖树减少 5 个包，供应链审计面缩小
- 消除"代码存在但从未工作"的误导：后续开发者不会再把它当成待上线功能评估排期

**负面 / 已知限制**

- **复活成本从"配置环境变量 + 补依赖"变成"从 git 历史恢复 + 重新接线"**：这是本次摘除的主要代价。缓解措施是 §4 的前置条件清单——它让复活不必从零推断
- 若采用"只删前端、保留服务端"的缩小范围，则 5 个依赖无法全部摘除（`ws` 本就不在依赖表中，但 `yjs`/`lib0`/`y-prosemirror` 仍被 `persistence.ts` 间接需要），提分幅度相应下降
- 摘除动作本身要同步更新多份引用文档（`SPEC.md`、`docs/design/INFORMATION-ARCHITECTURE-2026Q4.md`、`docs/ROADMAP-2026Q4.md`、`design/FEATURE-DESIGN-cloud-doc.md`、`api/openapi.yaml`、`web/messages/{zh,en}.json` 注释、`zero-coverage-baseline.txt`），遗漏会造成文档漂移

## 4. 复活协同的前置条件（原 ARCHIVE-NOTE.md §3 迁移至此）

> **本节是"复活实时协同"的唯一前置检查项。** 原 `server/collab/ARCHIVE-NOTE.md` 已随目录摘除删除，
> 其"复活前置条件"内容迁移至本节，避免知识断层。

### 4.1 三道独立的门，缺一不可

| # | 门 | 复活时的要求 |
|---|---|---|
| 1 | 服务端可运行 | 补 `ws` + `@types/ws`；`server/collab/` 需 `package.json` 并纳入 pnpm workspace 与 CI（含 lint/test） |
| 2 | 前端挂载 Provider | `web/app/` 下需有真实页面 import 并挂载 `CollaborationProvider` |
| 3 | 编辑器接入 CRDT | `RichTextEditor.tsx` 需接入 Collaboration 扩展（注意：与 StarterKit 的 `undoRedo` 互斥，需换历史管理架构） |

**三道门相互独立**：即使 1、2 完成而 3 未做，文档编辑仍不走 CRDT，只会产生"看起来接线了但没用"的中间态。

### 4.2 硬约束：S5 诚实化必须与挂载同批落地

`CollaborationProvider` 原有实现中，WS 地址未配置时**不是 fail-close，而是静默兜底** `ws://localhost:1234`。一旦挂载 Provider 而服务端未部署：

1. WS 连不上 → 状态在 offline ↔ connecting 间永久抖动（y-websocket 指数退避重连）
2. `PresenceIndicator` 的 offline 档用 `--warn`（amber）呈现
3. **用户看到一个永动的黄色警告条，会去查自己的网络** —— 而真相是服务端没部署

**这是接线后必然发生的误导，不是假设风险。**

因此：**任何挂载 `CollaborationProvider` 的改动，必须与 S5 判定在同一次提交落地**，两者不可拆分。

S5「实时协作未启用」态的三条硬约束：

1. **不提供「重试连接」按钮** —— 服务端未部署时重试结果相同，给必然失败的操作按钮是设计失职
2. **停掉重试动画** —— 永动 spinner 制造"正在努力连接"的错觉，比诚实说"没开"更糟
3. **用中性色（`--muted`）不用 `--warn`** —— 这是"没启用"，不是"你的网络坏了"

判定实现**只用 boolean state，不用时序阈值**：

```js
const [fromEverConnected, setFromEverConnected] = useState(false);
// wsProvider 首次成功 connect 时置 true，此后不再回 false
const isCollabUnavailable = !fromEverConnected && 连续失败次数 >= 3;
```

理由是两类错误的代价不对称：时序阈值在慢网络下会**误判**成"未启用" ⇒ **对正常用户说谎**；boolean 只会**漏判** ⇒ 继续显示加载态，代价仅是体验降级。漏判可接受，误判是诚实性事故。

### 4.3 复活前自检清单

- [ ] `ws` + `@types/ws` 已入依赖，服务端可实际启动
- [ ] `RichTextEditor` 已接入 Collaboration 扩展（否则 Provider 挂了也没用）
- [ ] S5 判定已实现，用 `fromEverConnected` boolean，非时序阈值
- [ ] S5 态下 `CollaborationCursor` 完全不渲染（不渲染占位）
- [ ] S5 态下光标色板完全不渲染
- [ ] `NEXT_PUBLIC_COLLAB_WS_URL` 未配置时不会静默兜底 localhost
- [ ] 鉴权代码已补测试覆盖（承接 §1 修订：原实现零执行零测试）

### 4.4 光标色板约束

原 `CollaborationProvider` 内 8 色离散光标 token（含 `--cursor-purple` / `--cursor-pink`）复活时需：

1. **改名去掉色相词**（如 `--collab-user-1-fg`），避免后续按色相检索时误判为"引入紫色主视觉"
2. **加约束注释**：仅用于多人协同区分用户身份；不得用于主视觉/CTA/品牌；不得组合为渐变；**S5 降级态下完全不渲染**

这 8 个离散纯色**不违反 P0-2**（红线禁止的是"紫色→粉色渐变作为主视觉"，且红线本身允许 Indigo/Slate Blue 作纯色），改名纯为下游工具防误判。

### 4.5 `--info` 语义色缺失

S2「正在重连」需要既非成功也非警告的色，而 `design/design-tokens.css` 当前只有 success/warn/danger 三族，**无 `--info`**。复活时需在 Primitive 块（唯一允许裸值的位置）新增 `--p-info` 及其 soft/fg 派生，且**不可派生自 `--accent`**（后者有"每屏 ≤2 处"的独立预算约束）。

## 5. 与能力边界表述的关系（需向用户如实说明）

本次摘除**不改变**已交付能力，但需修正一处对外表述：

- 此前表述为「保留**离线编辑** + 版本历史」
- 实际保留的是「**在线编辑** + 失焦保存 + 版本历史」

原因：`y-indexeddb` 虽是纯浏览器侧能力，但其唯一消费者 `CollaborationProvider` 全仓零挂载 ⇒ 该离线缓存从未激活。当前离线可达范围由 `web/public/sw.js` 决定——仅预缓存 `/dashboard` `/board` `/my-tasks` 三条核心路由，且明确不缓存 `/api/` 与 `/w/{wid}/…`。`DocumentEditor.tsx:463` 为 `onBlur={() => save()}`，无离线兜底 ⇒ **断网时文档编辑无法保存**。

这是能力边界的偏差，不是措辞偏差，已报用户知悉。
