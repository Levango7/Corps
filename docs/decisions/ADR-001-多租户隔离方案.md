# ADR-001: 多租户隔离方案

## Status

Accepted (2026-08-19) — 锁定，MVP 上线即生效。

## Background

corps 是对外多租户 SaaS（对标飞书，面向 5–30 人团队）。Spec 第 10 节将"数据隔离"列为 P0 红线，并给出两条不可违背的约束：

1. `workspace_id` 仅从 JWT 解析，绝不信任客户端传入。
2. 隔离必须由引擎层强制，应用层即使漏写 `WHERE workspace_id = ?` 也不能跨租户泄漏。

历史经验（Spec 第 11 节"多租户数据泄漏"坑）表明，纯应用层过滤在 Prisma/Next.js 组合下极易因漏写 WHERE 而泄漏。候选方案有三：

- **A. 独立数据库 / Schema 每租户**：隔离最强，但 MVP 成本与运维复杂度过高，且 Stripe 计费、跨租户统计难以统一。
- **B. 共享数据库 + 共享 Schema + `workspace_id` 列过滤（应用层）**：最省，但隔离依赖应用正确，不符合红线第 2 条。
- **C. 共享数据库 + 共享 Schema + `workspace_id` 列 + PostgreSQL RLS（引擎层）**：在 B 的基础上用 RLS 在引擎层兜底，应用漏写也不会泄漏。

## Decision

采用方案 **C（共享 Schema + `workspace_id` + PostgreSQL RLS）**，具体约定：

- 所有租户数据表（`members`, `tasks`, `comments`, `decisions`, `decision_versions`, `subscriptions`）含 `workspace_id UUID NOT NULL REFERENCES workspaces(id)`，并建 `idx_<table>_workspace_id` 索引。
- 每表 `ENABLE ROW LEVEL SECURITY`，策略 `USING (workspace_id = current_setting('app.workspace_id', true)::uuid)`，INSERT/UPDATE 加 `WITH CHECK` 防止写入其他租户。
- 请求级通过 `SET LOCAL app.workspace_id = <JWT.wid>` 注入租户上下文（仅在验证 JWT 后、事务内设置）。使用事务级连接池（PgBouncer）时 `SET LOCAL` 自动随事务结束复位，杜绝连接池串租户。
- 应用连接角色 `app_role`：`NOINHERIT`、`NOBYPASSRLS`、**不拥有任何表**，因此无法关闭 RLS 也无法 ALTER/DROP 表。
- 根表 `workspaces` 与身份表 `users`/`sessions` 为有意例外（`workspace_id` 不适用），改用 `app.user_id` 键的 RLS（`users`/`sessions` 额外保留 `app.auth_op` 登录/刷新窄逃生口，仅供 Better Auth 登录与 refresh 轮换查找）。
- 隔离必须有测试：覆盖 Spec AC-03（跨租户直接访问返回 404/403 且无泄漏）与 AC-04（漏写 WHERE 仍被 RLS 拦截），测试点已在 `db/schema.sql` 第 7 节标注。

## Consequences

正面：

- 引擎层强制隔离，应用层 Bug 不会造成跨租户数据泄漏（满足 AC-04）。
- 单库单 Schema，Stripe 计费按 `subscriptions.quantity` 同步、跨租户统计与运维成本低。
- `SET LOCAL` + 事务池化天然适配 Serverless/CloudBase 部署模型。
- 红线的两条约束均被结构强制：JWT 是唯一 `wid` 来源；`app_role` 无 BYPASSRLS。

负面 / 代价：

- 每个请求必须正确设置 GUC，否则 RLS 默认拒绝（缺失 GUC = 0 行），需要中间件/Route Handler 统一注入，增加一处必须正确的代码路径。
- RLS 对全表扫描类查询有轻微规划开销；已通过 `workspace_id` 索引缓解。
- `users`/`sessions` 的 `app.auth_op` 逃生口需在审计中盯紧，避免被误用扩大读取面。
- 未来需要跨租户管理后台时，须另建具备 BYPASSRLS 的管理角色并严格受控，不能复用 `app_role`。

## Related ADRs

- ADR-002（技术栈选型）：本隔离方案依赖 PostgreSQL 18.4 的 RLS 能力与 Next.js 全栈的 Route Handler 注入点。
- ADR-003（计费方案）：`subscriptions` 表按 `workspace_id` 隔离，Stripe webhook 写入时同样受 RLS 约束（以 `app.workspace_id` 注入上下文）。
