## 为什么要有这份台账

ADR 记录的是**已经拍定**的决策；这份台账记录的是**定不下来、或暂时不动、或已知但先接受**的事项。两者的区别是责任归属：

- ADR 的读者是"后来想知道当初为什么这么定"的人；
- 台账的读者是"后来想知道还有什么没解决"的人。

没有这份台账时，遗留项会散落在 PR 正文、提交信息、聊天记录里，最终随上下文一起消失。本文件是它们的固定落点。

## 三类固定 slug

| slug                            | 含义                                         | 典型判据                   |
| ------------------------------- | -------------------------------------------- | -------------------------- |
| `waiting-on-external-condition` | 等外部条件（用户确认、第三方审批、环境具备） | 卡点不在代码里             |
| `design-decision-to-evaluate`   | 设计待评估（需要对比或 POC）                 | 有多个可选解，尚无证据选边 |
| `existing-design-boundary`      | 现有设计的已知边界（接受，不修）             | 修它的代价大于收益         |

## 维护约定

1. **每个 Phase / 每个批次收尾时**，未决项必须复现到工作上下文最前面（带「N 未决 + M 已决」汇总），逐条判断能否关闭。
2. **关闭不等于删除**：行保留，`状态` 改 `RESOLVED`，`关闭日期` 填上，并在下方"已关闭"表留一行 Resolution。
3. **已关闭项若具备决策价值，升格为 ADR**（编号不复用，见 `docs/decisions/README.md`）。
4. 新增行必须写清「卡在什么上」与「何时可关闭」——只写"待办""后续处理"的条目没有关闭判据，等于没有登记。
