# ADR-008: 国际化（i18n）方案选型与范围界定

- **状态**：PROPOSED（2026-08-26 提交评审，待用户拍板）
- **提交**：平台能力决策分析师｜依据：SPEC.md §1（产品定义）、§3（明确不做）、§4（技术架构）、docs/market/product-roadmap.md M3、ADR-002（技术栈选型）
- **关联**：docs/analytics/FUNNEL-METRICS.md（触发条件的证据来源）、ADR-002、roadmap M3「国际化基础框架（中英双语）P2 1周」

## 1. 背景与核心问题

### 1.1 决策背景

roadmap M3 列入「国际化基础框架（中英双语）」P2 项，预估 1 周。但 SPEC 的定位与该条目存在张力，关键事实如下（均有出处）：

| 编号 | 事实 | 出处 |
|------|------|------|
| F1 | 目标用户为中国大陆 5–30 人中小团队 | SPEC §1 |
| F2 | 部署为腾讯云 CloudBase + 国内 CDN，「国内直连最优」 | SPEC §4 |
| F3 | 支付在评估替换 Stripe 为微信/支付宝（跨境可行性待定） | SPEC §10、§13；roadmap M3 P1「国内支付接入 2周」 |
| F4 | 「明确不做」清单锁定范围，i18n 未列入该清单也未列入 MVP 范围 | SPEC §2、§3 |
| F5 | roadmap 将 i18n 排在 M3，与全局搜索（P1 2周）、国内支付（P1 2周）、安全审计（P1）同期竞争资源 | product-roadmap.md M3 表 |
| F6 | 当前埋点无落地页/来源归因（landing_view 缺失），海外访客占比无任何数据可依 | web/app/api/v1/events/route.ts 白名单 + docs/analytics/FUNNEL-METRICS.md §3.1 |

### 1.2 核心问题

> **目标市场是中国大陆，是否值得现在投入 i18n？**

三个子问题：

1. **时机问题**：在没有任何海外需求信号的情况下提前建设，是否违反 SPEC §3「范围锁定」的精神？
2. **成本问题**：roadmap 估算「1 周」是否覆盖了 i18n 的真实成本？（框架引入 ≠ 双语可用）
3. **路径问题**：若启动，next-intl / react-i18next / 自研三者如何选？若不启动，何时必须重新审视？

### 1.3 成本真相：roadmap 的 1 周估算不成立

「国际化基础框架」若要达到「中英双语可用」的验收口径（用户可切换且全站无中文残留），真实工作量构成为：

表：i18n 真实工作量构成对照表

| 工作项 | 内容 | 估算 |
|--------|------|------|
| 框架引入 | 依赖、middleware/locale 路由段、字典加载、SSR 注水 | 0.5–1 周 |
| 文案抽取迁移 | 全站 UI 字符串迁入字典文件（估算 300–500 条：页面清单 6 类页面 × 导航/按钮/空状态/表单/错误态） | 1.5–2 周 |
| 服务端文案 | 错误 message 枚举、邮件模板（邀请邮件 sendInviteEmail 等）、通知文案 | 0.5 周 |
| 格式化改造 | 日期/数字/货币统一走 Intl 并按 locale 输出 | 0.5 周 |
| 英文翻译与校对 | 机翻初稿 + 人工审校（英文质量直接影响品牌感知） | 0.5 周 |
| 回归测试 | 双语 × 双主题 × 主要流程回归 | 0.5–1 周 |
| **合计** | — | **约 4–5.5 周** |

结论：「1 周」只够引入框架并迁移 1–2 个页面做样板，不足以交付双语能力。**本 ADR 要求将 roadmap 该条目的估算修正为 ≥4 周或改为条件触发项**（见 §6）。

## 2. 方案对比

四个候选：A. next-intl；B. react-i18next/i18next；C. 自研轻量 Context + 字典；D. 不做，推迟至触发信号出现。

### 2.1 总览对照

表：i18n 候选方案总览对照表

| 维度 | A. next-intl | B. react-i18next / i18next | C. 自研 Context + 字典 | D. 推迟不做 |
|------|--------------|----------------------------|------------------------|-------------|
| 包体积影响（客户端，估算值*） | ~9–12 KB minzip（use-intl 运行时），服务端部分不计入 client bundle | ~20–25 KB minzip（i18next core + react-i18next，不含插件） | < 2 KB | 0 |
| SSR/RSC 兼容性 | App Router 一等公民：[locale] 路由段 + RSC 内 getTranslations/useTranslations 直接可用 | 客户端组件成熟；RSC 下需 per-request instance 与额外胶水层，官方 App Router 路径摩擦较多 | 取决于自研实现质量；RSC/CC 边界传参、注水需自行解决 | — |
| 路由级 locale（SEO 友好 /en /zh） | 原生支持（URL 路径策略） | 需自行拼装（cookie/header 协商 + 手动路由） | 需自行实现全部机制 | — |
| 运行时切换灵活度 | 支持（cookie/URL 两种策略） | 最灵活（内存即时切换，无需路由变化） | 自行实现 | — |
| 迁移成本 | 中：新增 middleware + 全站路由包一层 [locale] 段，触碰所有页面路由 | 中低：Provider 包裹即可起步，不动路由；但 RSC 部分补课成本高 | 高：字典结构/插值/复数/类型安全/命名空间全部自造（此前已评估为工作量巨大） | 0 |
| 维护负担 | 低–中：跟随 Next 大版本升级有适配成本 | 低–中：生态插件多但版本矩阵复杂 | 高：全部长期自担 | 0 |
| ICU 消息格式 / 复数 / 插值 | 内置 | 内置 | 全部自造（中文无复数，英文有——自研易在此踩坑） | — |
| TypeScript key 类型安全 | 支持（v3.22+ 类型增强） | 可通过 TS 声明达成 | 自行实现 | — |

> \* 包体积为社区公开量级的估算值，非实测；若进入实施，以 spike 阶段 `npm run build` 产物实测为准。

### 2.2 方案 A：next-intl

- **优点**：App Router 原生支持是决定性优势——本项目 SPEC §4 锁定 Next.js App Router 全栈，RSC 内直接取译文的体验最顺；路由级 locale 对未来 SEO（hreflang/sitemap 分语言）是免费红利；ICU 格式内置。
- **缺点/风险**：
  1. 引入即要求 `[locale]` 路由重构，**所有页面路径变更**，与 M3 并行的其他 P1 项（全局搜索、国内支付页面）会产生合并冲突窗口；
  2. 对 next@16.2.6 的兼容性截至本文撰写**未经本项目验证**（社区库对 Next 大版本的适配通常滞后数周），列为启动前置 spike 项；
  3. 单语言期也要承担 middleware 与目录结构的认知负担。
- **适用前提**：确定要做双语且有 SEO 诉求。

### 2.3 方案 B：react-i18next / i18next

- **优点**：生态最大（插件、检测器、后端加载器齐全）；运行时切换零约束；不强制改 URL 结构，单语言期侵入最小。
- **缺点**：App Router 的 RSC 场景是其短板——Server Components 中同步取译文需要 per-request i18n instance、资源内联等胶水代码，官方指南复杂度明显高于 next-intl；本项目页面大量使用 RSC 数据获取模式（SPEC §4 锁定 App Router），意味着最难的场景恰好是它最弱的场景。
- **结论**：对本项目「客户端组件少、RSC 为主」的形态，B 是次优解。仅当未来出现「大量纯客户端 SPA 化页面」时才反超。

### 2.4 方案 C：自研轻量 Context + 字典

- **优点**：零依赖、体积最小、完全可控。
- **缺点**：此前已评估过工作量巨大——插值、复数规则（英文 one/other）、日期数字格式化、命名空间拆分、类型安全 keys、SSR 注水一致性全部自造；这些恰是 next-intl/i18next 十年打磨的核心。对当前规模的团队，维护负担将随功能增长线性上升。
- **结论**：否决。造轮子收益为负。

### 2.5 方案 D：推迟不做（触发条件驱动）

- **优点**：成本为零；符合 SPEC §3 范围锁定精神；把资源让位给 M3 的 P1 项（全局搜索 2 周 + 国内支付 2 周 + 安全审计，均为直接影响 GA 发布的事项）；避免在无需求证据时背上「每新增一个功能的文案都要 ×2 语言」的持续税。
- **缺点**：若触发信号突然出现（如大客户要求英文版），从零启动有 4–5 周交付周期，响应慢。缓解手段见 §4.3（预研结论前置锁定 + 防退化约定）。
- **关键配套**：推迟≠放任。需同时落地两件低成本事项：
  1. **防退化约定**（一次性 <0.5 天，写入 CODING-STANDARDS）：UI 文案禁用字符串拼接造句（保留完整短语便于未来整句抽取）；日期时间一律 `Intl.DateTimeFormat("zh-CN", …)`；货币符号走集中常量映射，禁止散落硬编码 "¥"；
  2. **数据信号采集**：按 FUNNEL-METRICS.md 补齐 landing_view（含 locale/referrer props），使 S1 触发条件（§4.2）可被度量。

### 2.6 对比结论

技术维度上 A（next-intl）优于 B 优于 C；但**时机维度上 D 优于立即实施**。两者不矛盾：D 是「现在做什么」，A 是「将来做的时候用什么」。本 ADR 将二者合并为一个决策：现在推迟，预研锁定 A 为启动首选。

## 3. 范围界定（若启动）

### 3.1 第一期纳入翻译的字符串

| 类别 | 具体内容 | 说明 |
|------|----------|------|
| 全局导航与外壳 | 侧边栏菜单、顶栏、工作区切换器、Cmd+K 命令面板分组标题 | 数量少、复用度高，优先迁移 |
| 通用按钮与操作 | 保存/取消/删除/邀请/复制链接/升级 等 | 集中定义于 common 命名空间 |
| 空状态引导文案 | 看板空列、任务详情空评论、决策记录空列表等 | SPEC §2 P0「空状态引导」同源资产，一并处理 |
| 认证页与错误提示枚举 | 登录/注册表单标签、服务端错误 code→message 映射表 | 服务端按请求 locale 返回对应语言 |
| 邮件模板 | 邀请邮件（sendInviteEmail）、催缴邮件（AC-09） | 按收件人 workspace locale 或默认 zh-CN |
| 计费页固定文案 | 套餐名、固定权益描述（价格数字本身不翻译） | 配合 M3 定价上线 |

### 3.2 永不翻译的范围（红线）

| 类别 | 示例 | 原因 |
|------|------|------|
| 用户生成内容（UGC） | 任务标题/描述、评论、@提及、决策记录 Markdown 正文 | 产品语义即「用户的语言」；机器翻译 UGC 成本高、风险大、价值存疑。**永久不做**，任何期都不翻 |
| 租户自定义数据 | 工作区名称、成员姓名、自定义字段值 | 同上 |
| 专有名词 | corps、工作区（产品术语表中定夺译名后全局一致）、Stripe 等第三方品牌 | 术语表统一管理 |

### 3.3 技术性配套

- 日期/时间/数字/货币：统一 `Intl.*` API 按 locale 输出（zh-CN / en-US）；时区业务口径沿用 FUNNEL-METRICS.md §6.4 的 Asia/Shanghai 规则（i18n 改变显示格式，不改变统计日界）。
- 字体：SPEC §8 已锁 Inter（拉丁）+ Noto Sans SC（CJK），en 环境自动退化为 Inter-only，无字体改造量。
- 图标：Lucide 通用，无本地化工作量。

## 4. 推荐结论

### 4.1 推荐

> **推荐方案 D：现在不做 i18n，将其从 M3 执行项改为条件触发项；预研结论锁定 next-intl（方案 A）为触发后的首选实现。**

理由链：

1. **市场与基础设施均指向国内**：SPEC §1 主市场中国大陆、§4 CloudBase 国内部署、§10/M3 正在推进支付本土化——同一时期投入双语与战略方向不自洽（事实 F1/F2/F3）。
2. **成本被低估**：roadmap 的 1 周估算只能买到「框架 demo」（§1.3），要么修正预算到 ≥4 周，要么改为条件触发——后者在无需求证据时明显更优（事实 F5）。
3. **无需求证据**：当前连 landing_view 都未埋点，海外访客占比无从谈起（事实 F6）。正确的顺序是先补齐归因埋点，用 4–8 周数据回答「要不要做」，而不是先拍板再做。
4. **YAGNI 与 SPEC 精神一致**：SPEC §3 以「范围锁定」为纪律，i18n 在无信号时启动属于典型的提前优化。
5. **推迟的响应速度风险已被对冲**：§2 的对比即预研产出，触发后可直接进入 spike，节省重复调研的 2–3 天；防退化约定保证未来的文案抽取成本不随时间恶化。

### 4.2 触发条件（任一满足即重开本 ADR 进入实施评审）

| 编号 | 信号 | 度量方式 | 阈值 |
|------|------|----------|------|
| S1 | 海外流量信号 | 自有埋点 landing_view.props.locale/referrer 聚合：非大中华区 session 占比 | 连续 4 周 ≥ 5% |
| S2 | 需求信号 | 海外/跨境团队主动注册或邮件询盘英文版 | 累计 ≥ 3 个独立团队 |
| S3 | 商业信号 | 渠道合作、分发平台或投资条款明确要求多语言 | 出现即触发 |
| S4 | 战略信号 | 公司层面决定出海（如新加坡/北美市场） | 出现即触发 |

### 4.3 触发后的分期计划（预锁定）

| 期 | 内容 | 预算 |
|----|------|------|
| Spike（1 周内完成） | 验证 next-intl × next@16.2.6 兼容性；[locale] 路由 PoC；bundle 实测 | 2–3 人日 |
| 第一期 | §3.1 范围：导航/按钮/空状态/auth/错误枚举/邮件模板，zh+en 双语 | 2 周 |
| 第二期 | 全站剩余静态文案 + Intl 格式化收尾 + 双语回归 | 1.5–2 周 |
| 持续 | 新功能文案双语同步进 Definition of Done | 持续税 |

## 5. 时间估算与风险

### 5.1 本决策（方案 D）自身的执行成本

- CODING-STANDARDS 增补防退化三条约定：<0.5 人日；
- FUNNEL-METRICS.md 中 landing_view 埋点本就在 P0 清单，无额外成本；
- roadmap 条目修订（§6）：10 分钟。

### 5.2 若无视本建议、坚持在 M3 实施（备选路径 B）

- 预算下限 4 周（§1.3），且建议与 M3 的 P1 项错峰（先做完全局搜索再动路由，避免 [locale] 重构撞车）。

### 5.3 风险登记

表：i18n 决策风险登记表

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 触发信号出现晚于融资/销售节奏，4–5 周交付期来不及 | 中 | 中 | S3/S4 即时触发通道 + 预研已锁定，压缩启动准备至 1 周内 |
| next-intl 对 next@16.2.6 存在兼容缺口 | 低–中 | 中（仅触发后） | spike 前置；fallback 到 react-i18next（客户端优先策略）或等待上游适配 |
| 推迟期间文案持续硬编码，未来抽取成本膨胀 | 中 | 中 | 防退化约定 + 整句原则（§2.5）；每季度在评审时抽查 |
| 英文文案质量损害品牌（Calm Precision 定位对标 Stripe/Linear） | 中 | 中 | 触发后预算含人工审校，禁止纯机翻上线 |

## 7. Consequences（后果）

- **正面**：M3 释放约 1 周名义预算给 P1 项；决策依据从「roadmap 惯性」变为「数据信号」；启动路径与技术选型已预锁定，消除未来的重复调研成本。
- **负面/代价**：接受「若有突发海外需求，响应周期 4–5 周」的机会成本；防退化约定依赖团队自觉，存在执行漂移风险（以季度抽查缓解）。
- **中性**：AnalyticsEvent/埋点体系不受影响；UGC 永不翻译的红线在任何后续方案中不变。
