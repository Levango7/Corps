## 1. 背景与评估范围

M1（MVP）+ M2（工程化）+ M3（公开发布）阶段已完成，产品进入 v2 前瞻期。SPEC §3「明确不做」清单锁定了 5 个 v2 候选功能及其触发条件。本 ADR 对这 5 个功能进行技术可行性评估、优先级排序，并启动优先级最高的第一期功能 MVP。

### 1.1 评估对象

| 编号 | 功能 | 路线图定位 | 触发条件 |
|------|------|-----------|----------|
| F1 | IM 轻沟通（任务上下文即时通讯） | v2 早期 | 用户反馈"任务上下文需要快速轻沟通" |
| F2 | 决策协同编辑（CRDT/OT） | v2 中期 | 活跃团队 ≥50 且决策编辑频率 ≥5次/天/团队 |
| F3 | 日历集成（Google/Outlook） | v2 中期 | 日历需求 ≥20% 用户反馈 |
| F4 | SSO/SAML 企业认证 | 企业版 | 企业客户 ≥3 家且合同签定 |
| F5 | AI 智能助手 | 远期 | 数据积累 ≥1000团队 + 有算力预算 |

## 2. 逐功能可行性评估

### 2.1 F1：IM 轻沟通

**定位**：任务上下文内的轻量即时通讯，非独立 IM 系统。

#### 2.1.1 技术可行性：中

| 维度 | 评估 |
|------|------|
| 实时通信方案 | Next.js Route Handler 无原生 WebSocket；可选 SSE（单向推送）+ HTTP POST（发消息）或轮询降级。MVP 用轮询（5s 间隔 + `?since=` 游标），零运维增量；后续升级 SSE + Redis pub/sub 跨实例广播 |
| 消息存储模型 | 新增 `Message` 模型，复用 Comment 的 workspaceId/taskId/authorId 模式，RLS 自动覆盖 |
| 前端集成点 | 任务详情页已有评论区，新增「聊天」区域，UI 模式成熟 |
| 部署兼容性 | 轮询方案对 CloudBase 无特殊要求；SSE 需验证长连接超时配置 |

#### 2.1.2 预估工作量：3–4 人周

| 工作项 | 估算 |
|--------|------|
| 数据模型 + Prisma 迁移 | 0.3 周 |
| REST API（GET 历史 + 增量 / POST 发送） | 0.5 周 |
| 前端聊天 UI（消息列表 + 输入 + 轮询 + 滚动） | 1.5 周 |
| i18n 文案 + 通知集成 | 0.3 周 |
| 测试 + 构建验证 | 0.4 周 |
| 合计 | 约 3 周 |

#### 2.1.3 技术依赖与风险

- **低风险**：轮询方案无新依赖，复用现有 HTTP API 模式
- **中风险**：未来升级 SSE/WebSocket 时需引入实时通信层 + Redis pub/sub，但 API 设计预留 `?since=` 游标可无缝升级
- **无阻断依赖**

#### 2.1.4 对现有架构的影响：低

- 新增 1 个 Prisma 模型（Message），不改现有模型
- 新增 2 个 API 路由（messages GET/POST），不改现有路由
- 任务详情页新增 UI 区域，不改现有布局结构
- RLS 自动覆盖（Message 含 workspaceId）

#### 2.1.5 用户体验提升：高

任务上下文内即时沟通是高频痛点——当前评论是异步的（发完等刷新），用户反馈"任务上下文需要快速轻沟通"的触发条件最易满足。

### 2.2 F2：决策协同编辑（CRDT/OT）

**定位**：多人同时编辑决策记录，实时冲突解决。

#### 2.2.1 技术可行性：中低

| 维度 | 评估 |
|------|------|
| CRDT 库选型 | Yjs（生态成熟）或 Automerge（去中心化）；Yjs + yjs-server 是主流路径 |
| 服务端同步 | 需独立 WebSocket 服务（hocuspocus/y-websocket-server），Next.js Route Handler 无法承载 |
| 冲突解决 | CRDT 自动解决，但需处理 Markdown 富文本的 Yjs binding（y-prosemirror 或 y-monaco） |
| 现有架构差距 | 当前决策记录是单编辑 + 版本留痕（DecisionVersion），升级到 CRDT 是架构性变更 |

#### 2.2.2 预估工作量：6–8 人周

| 工作项 | 估算 |
|--------|------|
| Yjs 服务端（hocuspocus + Redis 持久化） | 1.5 周 |
| 前端协同编辑器（y-prosemirror + Markdown binding） | 2.5 周 |
| presence（在线用户/光标位置） | 1 周 |
| 与现有 Decision/DecisionVersion 模型融合 | 1 周 |
| 测试 + 回归 | 1 周 |
| 合计 | 约 7 周 |

#### 2.2.3 技术依赖与风险

- **高风险**：引入独立 WebSocket 服务增加运维复杂度；Yjs 对 Next.js 16 RSC 边界处理需验证
- **中风险**：CRDT 文档持久化到 PostgreSQL 需自定义 adapter（Yjs 原生用 LevelDB/Redis）
- **阻断依赖**：触发条件未满足（需活跃团队 ≥50 且编辑频率数据）

#### 2.2.4 对现有架构的影响：高

- 需新增独立协同编辑服务（突破 Next.js 全栈单体架构）
- Decision 模型需重构（从单编辑版本流 → CRDT 文档状态）
- 前端编辑器从 textarea → ProseMirror，组件级重写

#### 2.2.5 用户体验提升：中

当前版本留痕（每次保存生成新版本）已能满足多数决策记录场景；协同编辑的增量价值在"多人同时编辑同一决策"的高频场景，当前数据不足以证明该频率。

### 2.3 F3：日历集成（Google/Outlook）

**定位**：任务截止日期同步到外部日历。

#### 2.3.1 技术可行性：中

| 维度 | 评估 |
|------|------|
| OAuth2 授权 | Better Auth Account 模型已支持多 provider（issuer + accountId），可扩展 Google/Microsoft OAuth |
| Calendar API | Google Calendar API / Microsoft Graph API 均有成熟 SDK |
| 双向同步 | 单向（corps → 日历）简单；双向（日历 → corps）需 webhook + 冲突处理 |
| RRULE 深坑 | 重复事件 RRULE 解析复杂（SPEC §3 已标注），MVP 只同步非重复任务的截止日期 |

#### 2.3.2 预估工作量：4–5 人周（单向同步 MVP）

| 工作项 | 估算 |
|--------|------|
| OAuth2 授权流程（Google + Microsoft） | 1.5 周 |
| Calendar 同步服务（任务 dueDate → 日历事件） | 1 周 |
| 同步状态管理 + 错误重试 | 0.5 周 |
| 前端设置页集成（授权/取消授权/同步状态） | 1 周 |
| 测试 | 0.5 周 |
| 合计 | 约 4.5 周 |

#### 2.3.3 技术依赖与风险

- **中风险**：OAuth2 token 刷新 + 长期同步一致性；Google/Microsoft API 限流
- **低风险**：Better Auth 扩展 OAuth provider 是标准路径
- **阻断依赖**：触发条件未满足（日历需求 ≥20% 用户反馈）

#### 2.3.4 对现有架构的影响：低–中

- 新增 OAuth provider 配置 + Calendar 同步服务（可作为定时任务/队列 worker）
- Account 模型已就绪，无需 schema 变更
- 前端设置页新增日历集成区域

#### 2.3.5 用户体验提升：中

截止日期同步到日历有用，但非核心闭环；用户可通过手动方式（复制日期）达到类似效果。

### 2.4 F4：SSO/SAML 企业认证

**定位**：企业微信/钉钉/SSO 单点登录。

#### 2.4.1 技术可行性：高

| 维度 | 评估 |
|------|------|
| OIDC 路径 | 企业微信/钉钉均提供 OIDC 接口，Better Auth 原生支持 OAuth/OIDC provider |
| SAML 路径 | SAML 2.0 协议复杂（XML 签名/加密/断言），需引入 saml2-js 等库 |
| 多 IdP 配置 | Account 模型 issuer + accountId 唯一键已支持多 IdP |
| 现有架构契合 | Better Auth 的 Account 模型正是为此设计 |

#### 2.4.2 预估工作量：3–4 人周（OIDC 单 IdP）/ 6–8 人周（SAML + 多 IdP）

| 工作项 | OIDC | SAML |
|--------|------|------|
| IdP 配置 + 授权流程 | 1 周 | 2.5 周 |
| 用户映射 + 自动建工作区 | 0.5 周 | 0.5 周 |
| 前端登录页 SSO 入口 | 0.5 周 | 0.5 周 |
| 多 IdP 配置管理 | 0.5 周 | 1.5 周 |
| 测试 | 0.5 周 | 1 周 |
| 合计 | 约 3 周 | 约 6 周 |

#### 2.4.3 技术依赖与风险

- **低风险**（OIDC）：Better Auth 标准扩展路径
- **中风险**（SAML）：XML 安全（签名验证/重放攻击）+ IdP 兼容性测试矩阵
- **阻断依赖**：触发条件明确未满足（企业客户 ≥3 家且合同签定）

#### 2.4.4 对现有架构的影响：低

- Account 模型已就绪，OIDC 路径几乎无 schema 变更
- SAML 需新增 SAML 断言解析 + 证书管理

#### 2.4.5 用户体验提升：低（当前阶段）

仅对企业客户有意义；当前用户群（5–30 人中小团队）以邮箱注册为主。

### 2.5 F5：AI 智能助手

**定位**：任务摘要/自动分类/智能推荐。

#### 2.5.1 技术可行性：中

| 维度 | 评估 |
|------|------|
| LLM API 集成 | 技术上直接（OpenAI/Claude/国内通义/文心 HTTP API） |
| prompt 工程 | 任务摘要/分类的 prompt 模板需迭代调优 |
| 成本控制 | 按调用计费，需做用量配额 + 缓存 + 降级策略 |
| 数据隐私 | 任务内容发送给 LLM 供应商需用户授权 + 数据处理协议 |

#### 2.5.2 预估工作量：4–6 人周（基础摘要/分类）

| 工作项 | 估算 |
|--------|------|
| LLM 服务封装 + prompt 模板 | 1 周 |
| 任务摘要 API + 缓存 | 0.5 周 |
| 自动分类（标签/优先级建议） | 1 周 |
| 前端 AI 助手 UI（摘要面板/建议浮层） | 1.5 周 |
| 用量配额 + 成本控制 | 0.5 周 |
| 测试 | 0.5 周 |
| 合计 | 约 5 周 |

#### 2.5.3 技术依赖与风险

- **高风险**：数据隐私合规（任务内容含商业敏感信息，发送给第三方 LLM 需用户明确授权）
- **中风险**：LLM 输出不确定性（幻觉/格式不稳）需后处理校验
- **运营风险**：LLM API 成本是持续支出，需配额机制
- **阻断依赖**：触发条件远未满足（数据积累 ≥1000团队 + 算力预算）

#### 2.5.4 对现有架构的影响：低–中

- 新增 AI 服务调用层（独立 lib/ai.ts + API 路由）
- 不改现有数据模型，但需新增用量配额表

#### 2.5.5 用户体验提升：中

摘要/分类有价值，但依赖数据积累才能提供有意义的结果；当前用户量不足以训练/调优。

## 3. 优先级排序矩阵

表：v2 功能优先级排序矩阵

| 功能 | 触发条件成熟度 | 用户价值 | 开发成本 | 价值/成本比 | 技术风险 | 架构契合度 | 综合优先级 |
|------|--------------|---------|---------|-----------|---------|-----------|-----------|
| F1 IM 轻沟通 | 高（反馈即触发） | 高 | 低（3周） | 高 | 低 | 高 | **P1 — 第一期** |
| F3 日历集成 | 低（未到 20%） | 中 | 中（4.5周） | 中 | 中 | 中–高 | **P2 — 第二期** |
| F2 决策协同编辑 | 低（需 ≥50 团队） | 中 | 高（7周） | 低 | 高 | 低 | **P3 — 第三期** |
| F4 SSO/SAML | 低（无企业合同） | 低（当前） | 低–高 | 低 | 低–中 | 高 | **P4 — 企业版条件触发** |
| F5 AI 助手 | 极低（无数据/预算） | 中 | 中（5周） | 低 | 高 | 中 | **P5 — 远期** |

### 3.1 排序理由

1. **F1 IM 轻沟通排第一**：触发条件最易满足（用户反馈即可），用户价值最高（任务上下文即时沟通是高频痛点），与现有架构契合度最高（复用 Comment 模式 + Notification 系统 + RLS），开发成本最低（3 周），技术风险最低（轮询方案零新依赖）。

2. **F3 日历集成排第二**：技术风险可控，架构影响小，但触发条件未满足且用户价值中等。适合作为 IM 之后的增量。

3. **F2 决策协同编辑排第三**：投入大（7 周），架构影响高（需独立 WebSocket 服务），当前版本留痕已够用。需数据验证触发条件后再启动。

4. **F4 SSO/SAML 排第四**：技术可行性高但触发条件明确未满足（无企业合同）。等企业客户信号后启动，OIDC 路径可快速交付。

5. **F5 AI 助手排第五**：触发条件远未满足（无数据积累、无算力预算），数据隐私合规风险高。远期启动。

## 4. 第一期启动决策：IM 轻沟通 MVP

### 4.1 决策

启动 **F1 IM 轻沟通** 的 MVP 级实现。

### 4.2 MVP 范围界定

表：IM MVP 范围界定

| 维度 | MVP 包含 | MVP 不包含（后续迭代） |
|------|---------|---------------------|
| 实时方案 | 轮询（5s 间隔 + `?since=` 游标增量拉取） | SSE / WebSocket + Redis pub/sub 跨实例广播 |
| 消息类型 | 纯文本 | 富文本 / 图片 / 文件 / @提及 |
| 通知集成 | 新消息写入 Notification 表 | 实时桌面通知 / 浏览器 push |
| 消息范围 | 任务级（绑 taskId） | 工作区级 / 私聊 / 群组 |
| 历史管理 | 最近 200 条 + 增量游标 | 分页 / 搜索 / 导出 |
| 已读状态 | 不做 | 已读回执 / 在线状态 presence |

### 4.3 技术方案概要

#### 4.3.1 数据模型

新增 `Message` 模型：

```prisma
model Message {
  id          String   @id @default(uuid()) @db.Uuid
  taskId      String   @map("task_id") @db.Uuid
  workspaceId String   @map("workspace_id") @db.Uuid
  authorId    String?  @map("author_id") @db.Uuid
  body        String   @db.Text
  createdAt   DateTime @default(now()) @db.Timestamptz @map("created_at")

  task      Task      @relation(fields: [taskId], references: [id], onDelete: Cascade)
  workspace Workspace @relation(fields: [workspaceId], references: [id], onDelete: Cascade)
  author    User?     @relation(fields: [authorId], references: [id], onDelete: SetNull)

  @@index([taskId, createdAt])
  @@index([workspaceId])
  @@map("messages")
}
```

#### 4.3.2 API 端点

| Method | Path | 功能 |
|--------|------|------|
| GET | /api/v1/workspaces/:wid/tasks/:id/messages | 消息历史（?since=ISO 游标增量拉取） |
| POST | /api/v1/workspaces/:wid/tasks/:id/messages | 发送消息 |

#### 4.3.3 前端集成

任务详情页新增「聊天」区域（位于评论上方），5 秒轮询新消息，自动滚动到底部。

#### 4.3.4 i18n

新增 `chat` 命名空间到 `web/messages/zh.json` + `en.json`。

### 4.4 升级路径

```
MVP（轮询）→ v2.1（SSE + Redis pub/sub）→ v2.2（WebSocket + presence + 已读回执）
```

API 设计的 `?since=` 游标参数保证轮询到 SSE 的无缝升级——前端只需把轮询换成 EventSource，API 响应格式不变。
