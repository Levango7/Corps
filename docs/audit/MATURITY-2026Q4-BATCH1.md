## 1. 先说清楚：之前为什么没法验收

`docs/ROADMAP-2026Q4.md` 把验收判据写成一句：**「成熟度评分提升」**。
但仓库里从来没有一个能跑的评分器：

| 问题 | 事实 |
|---|---|
| 分数是人工打的 | 基线 `FULL-AUDIT-2026-09-27.md §2` 的八维度分是手感分，没有计算口径 |
| 分母自认不成立 | 同文件第 35 行写着：**「综合 ~~8.4/10~~ → 本行不再作为结论使用」**，原因是安全维度 9.0 的依据已被 09-29 复核推翻 |
| 无法重跑 | 没有脚本、没有快照，09-27 的分数无法在今天复现，也就无法证明"提升" |

结果是：**谁都可以说自己提升了，也没人能证伪。** 这不是交付质量的问题，
是判据本身设计错了 —— 用了一个既不可复现、又已自我否定的量当尺子。

### 本批次的修正

新增 `scripts/score_maturity.py`，把成熟度从感受题变成计算题。三条硬约束：

1. **只用机器判据** —— 每一项要么跑仓库自带的门禁脚本（退出码 0 即过），
   要么数仓库里的文件/行/匹配，要么断言产物存在。没有"基本完成""大致达标"。
2. **口径对齐仓库已提交的承诺** —— burn-down 相关项直接读
   `scripts/burndown-plan.txt` 里已 commit 的 `start/target/due/grace_days`，
   不另立标准，也不给"改数字变绿灯"留口子。
3. **不掩盖** —— 跑不起来的项标 **SKIP 并写明原因**，
   SKIP 不计入分子**也不计入分母**（所以它不会抬高分数，只会缩小口径）。

评分模型：单项 PASS=1.0 / WARN=0.5 / FAIL=0.0；维度分 = 10 × Σ权重 / 计入项数；
综合分 = 8 维度等权算术平均；档位 Gold ≥ 9.0 ＞ Silver ≥ 7.5 ＞ Bronze ≥ 6.0 ＞ Red。

## 4. 但有三个维度没动，其中 API 层是**退步**

这是本报告最重要的部分 —— 只报增量不报退步，等于把评分器又做成了宣传工具。

### 4.1 API 层：5.00 → 3.33（**−1.67**）

覆盖率名义上从 28.3% 涨到 30.4%，但看拆解就明白了：

- 路由处理器从 289 涨到 **292**（还在长）
- 已声明 path 从 81 涨到 **88**（补了 7 个）
- 未声明从 205 降到 **201**（只清了 4 个）
- **新增速度 ≈ 补齐速度**，覆盖率原地踏步

更糟的是 `api/openapi.yaml` 第 12 行那句自述：

```
Coverage: this contract declares 80 paths (updated 2026-09-27).
```

实测 88，**漂移从 1 扩大到 8**。这不是新问题（09-27 就漂了），但整整一个批次
没有收敛，反而扩大了。契约文件里写着错的覆盖数字，比没有契约更危险 ——
它会让人以为已经对齐了。

**建议：下一批把验收口径从"评分提升"换成两个不可作弊的量 ——
零行覆盖文件数（必须下降）+ 契约未声明路由数（必须下降）。**
这两个都是数出来的，不能靠改判据变好看。

### 4.2 数据层：5.00 → 5.00（Red）

RLS 部分全部 PASS（81 张表 ENABLE + FORCE + 有策略，双层防线完整）。
拖住这个维度的是一条新发现的 FAIL：

**`db/schema.sql` 快照落后最新迁移 1 个。** 文件头自述「对应迁移:
`20261019000000_add_user_locale`」，而最新迁移是 `20261022000000_add_workspace_settings`。
实测 `db/schema.sql` 里搜不到任何 `settings` 列 —— 快照缺了 `workspaces.settings`。

注意 `check_schema_migration_drift.py` 是 **PASS** 的，说明它只管
Prisma schema ↔ migrations 的漂移，**不覆盖 `db/schema.sql` 这份快照**。
这是个真实的门禁盲区：schema.sql 是给运维和 `runWithWorkspace` 守卫测试当权威参考的，
它陈旧等于给排障的人一份过期的地图。
